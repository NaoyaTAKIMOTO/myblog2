## 練習前夜に、表と睨めっこする時間

バンドのセットリストを決めるとき、実際にやっていることは単純ではありません。

メンバーが曲ごとにパートを持ち替えるバンドでは、曲順を1つ入れ替えるだけで転換の回数が変わります。ドラムの担当が変わる曲を続けて置けば、そのたびにセットを組み替えることになります。逆に、同じドラムの曲を固めれば転換は減るけれど、盛り上がりの流れは悪くなります。

さらに持ち時間があります。「40分演奏したら休憩」というルールを決めても、どの曲の後で切るかは勘です。曲順を直すたびに合計時間を計算し直し、休憩を入れ直し、また曲順を直す。この往復が、練習前夜の数十分を占めていました。

**SetlistAutomation** は、この作業を「スプレッドシートを埋める → 実行する → 出てきた案を直す」に置き換えるスクリプトです。ここでは、編成に付きまとう3つの制約と、それぞれをどう外したかを書きます。

## 既存手段の限界

| 手段 | できること | 限界 |
|---|---|---|
| 表を見ながら手で並べる | 盛り上がりや曲の相性を考慮できる | 隣接ペアしか見ないので全体の転換コストは最小にならない。曲順を変えるたびに合計時間を計算し直す |
| 表計算の並べ替え・フィルタ | 同じ担当の曲をまとめられる | 転換の重み（ドラムかベースか）を扱えない。休憩位置は結局手で決める |
| 総当たりで順列を試す | 転換コストの最小解が保証される | 曲数に対して階乗で増えるため、実用的な曲数で回らない |

手作業の最大の問題は、時間ではなく**再現性**です。なぜその順番にしたのかが残らず、次回もう一度考え直すことになります。

設計の要点は3つです。

- **曲順は最適化に任せる**: 転換コストを N×N の行列にし、TSP として解く
- **持ち時間は後処理**: 曲順が決まってから、曲長を積み上げて40分で区切る
- **休憩は重い転換に合わせる**: 15分の休憩でドラム交代を吸収できるなら、休憩位置を数曲ぶんずらす

曲順と休憩を同時に最適化しないのは、目的が違うからです。曲順は転換コストの合計を下げる問題、休憩は「重い転換をどこで行うか」の問題です。分けて解いたほうが、結果の理由を説明しやすくなります。

## 実装の要点

### 1. 曲表をそのまま入力にする

入力は Google スプレッドシートです。4行目をヘッダー、5行目以降を曲データとして読み、ステータスで対象を絞ります。`main.py` は `成立` の曲だけを対象にします。

```python
# main.py（データ読み込み）
        header = all_values[3]
        song_data_rows = all_values[4:]
        header_map = {h.strip(): i for i, h in enumerate(header)}
        ...
            status = row[status_col_idx].strip()
            if status.lower() != '成立': continue
```

ローカル版の `local_main_youtube.py` は、まだメンバーが埋まっていない曲も含めて案を作れるように、対象ステータスを増やしています。データ開始行も8行目に変わります。

```python
# local_main_youtube.py（設定項目）
TARGET_STATUSES = [
    "成立",
    "あと一人",
    "募集中",  # 必要に応じてコメント解除
]
HEADER_ROW_NUMBER = 4
DATA_START_ROW = 8
```

「成立」だけに絞ると、候補が足りずに短いセットリストしか作れません。「あと一人」の曲を混ぜた案を先に作っておけば、メンバーが埋まった時点でそのまま採用できます。

### 2. 転換コストを行列にして、曲順はソルバーに任せる

パートごとの重みは、ドラム5、ギター3、ベースとキーボード2、ボーカル・コーラス・その他1です。曲 A から曲 B へのコストは、交代したパートの重みの最大値になります。

```python
# local_main_youtube.py（create_cost_matrix）
    for i in range(num_songs):
        for j in range(num_songs):
            if i == j:
                continue
            members_i = songs_data[i]["ParsedMembers"]
            members_j = songs_data[j]["ParsedMembers"]
            cost, is_drum_change = calculate_transition_cost(
                members_i, members_j, costs_dict
            )
            cost_matrix[i, j] = cost
            if is_drum_change:
                drum_change_transitions_set.add((i, j))
```

この行列を OR-Tools の TSP に渡すと、総コストが小さい順序が返ります。手作業では隣接ペアの改善しかできませんでしたが、ソルバーは全体の合計を見て並べ替えます。ドラム交代の遷移は別の集合にも記録しておき、後の休憩挿入で使います。

### 3. 休憩は「時間」ではなく「重い転換」に合わせる

`main.py` の休憩挿入は素直です。ブロックの累積時間に次の曲を足して40分を超えるなら、その曲の前に休憩を入れます。このとき、境目の転換コストは0として数えます。入れ替えは休憩中にできるからです。

`local_main_youtube.py` はここを一段深くしています。40分を超えそうでも、3曲先までにドラム交代があれば、10分の超過を許して休憩をそこまで遅らせます。

```python
# local_main_youtube.py（設定項目）
lookahead_steps = 3  # 休憩判断時に何曲先までのドラム転換を考慮するか
break_time_allowance = 10  # 休憩を遅らせる場合に許容する時間超過(分)
```

```python
# local_main_youtube.py（create_detailed_setlist_with_breaks）
                            estimated_time_at_future_drum_change = (
                                current_block_time + time_accum_for_delay_check
                            )
                            if (
                                estimated_time_at_future_drum_change
                                <= play_time_limit + break_time_allowance
                            ):
```

ドラム交代は最も重い転換です。それを15分の休憩の中で済ませられれば、転換コストの合計は下がり、演奏も止まりません。持ち時間を絶対の制約にせず、少しだけ緩めることで「重い転換を休憩に隠す」余地が生まれます。

## 結果

リポジトリには削減率や実行時間の記録がないため、数値の比較は出せません。実装から言える変化だけを挙げます。

| 項目 | 手作業 | SetlistAutomation |
|---|---|---|
| 曲順の根拠 | 隣接ペアの目視 | 転換コスト行列と TSP の解 |
| 合計時間 | 曲順を変えるたびに計算 | 曲長の積み上げで自動計算 |
| 休憩位置 | 勘で決める | 40分＋許容10分の範囲で、ドラム交代の直前に寄せる（先読み対応版） |
| 記録 | 残らない | 別シートに曲順・転換コスト・実質コスト・合計時間を出力 |

作業としては、曲順を考える時間が「表を埋める時間」に変わり、比較と修正だけが残ります。先読み対応版では、休憩の位置が「40分になったところ」ではなく「ドラム交代の前」に寄るので、転換の重い箇所が演奏の流れを止めません。

## 向かないケース・残課題

- **曲数が少ない、転換がほぼ無いバンド**: 数曲しかなく楽器の持ち替えもなければ、手で並べたほうが速いです。ソルバーを使う意味は転換コストの差が大きいときに生まれます。
- **曲の途中でパートが変わる曲**: コストは曲間の遷移として定義しているため、1曲の中で担当が入れ替わるケースは表現できません。
- **YouTube に音源がないオリジナル曲**: 曲長が取得できず、既定の5.0分で見積もられます。全体の合計時間は粗くなります。
- **転換コストの単位**: 重みは1〜5の無次元の値ですが、ブロック時間の計算では分として加算しています。そのため「総時間」は目安で、実際の転換時間を反映した値ではありません。
- **MC や転換の実測が入らない**: 曲間のトークや、実際に何分かかったかは入力に含まれません。実測値を重みに反映させる仕組みは未実装です。
- **README と実装のずれ**: README は `main.py` を前提にデータ開始行を5行目と説明していますが、ローカル版は8行目です。動かすスクリプトによって表の読み方が変わります。

## まとめ

- 転換コストを数値の行列にすれば、曲順決めは TSP という既知の問題に落ちる
- 持ち時間と休憩は曲順の後処理にする。目的が違う制約を1つの問題に詰め込まない
- 休憩は「時間が来た場所」ではなく「重い転換を吸収できる場所」に置くと、同じ曲順でも合計コストが下がる

特別なアルゴリズムを実装したわけではありません。制約をどう表現するかを決めたことで、毎回の編成が再現できる手順になりました。
