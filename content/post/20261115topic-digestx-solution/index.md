## タイムラインを「読む」時間が確保できない

朝、通勤中にタイムラインを開く。昼には別の話題が流れ、夜には何が議論になったのか分からなくなる。フォローを増やすほど情報は増えるのに、読める量は増えません。

この困りごとは、3つの工程に分解できます。

1. **探索**: どの投稿が自分の関心に合うか、開いてみるまで分からない
2. **読み込み**: 合っていても、長いスレッドや引用の連鎖を追うのに時間がかかる
3. **整理**: 読んだ内容を「今日の論点」として頭の中でまとめ直す必要がある

TopicDigestX は、この3つをサーバー側へ移す試みです。キーワードをトピックとして登録しておき、収集・要約・整形を自動で回して、ダイジェストだけを読む形にします。現状は基盤の実装までで、収集と要約はこれからです。

## 既存手段の限界

| 手段 | できること | 限界 |
|---|---|---|
| タイムラインをそのまま追う | 文脈ごと読める | 読む量は減らない。開いた時点の順序で流れて消える |
| リスト・検索で絞る | フォロー外も含めて拾える | 絞っても読む作業は自分に残る |
| まとめサイト・ニュースレター | 要点だけ読める | 自分の関心テーマに合わせてはくれず、粒度も選べない |
| ブックマーク・後で読む | あとから辿れる | 溜まるだけで、読む時間は結局あとで必要 |
| LLM にコピペして要約 | その場で要約できる | 毎回コピーする手間。対象もその回限り |

どれも「読む」工程そのものを消してはいません。消せるのは、読む前の探索と、読んだ後の整理です。

設計の判断は3つです。

- **関心は保存する**: 毎回キーワードを打つのではなく、トピックとして DB に置く
- **重い工程はサーバーに寄せる**: 収集と要約を、読む人の待ち時間から切り離す
- **出力はダイジェストに固定する**: 読む量を先に決めてから読む

トレードオフもはっきりしています。速報性は収集の粒度に依存して落ちます。要約は圧縮なので、原文のニュアンスや反論の文脈は落ちます。その代わり、読む前に「読む価値があるか」を判断できるようになります。

## 実装の要点

### 1. 関心を1行のデータにする

```python
# backend/model.py
class Topic(Base):
    __tablename__ = "topics"
    id = Column(Integer, primary_key=True, index=True)
    name = Column(String, index=True, nullable=False)
    keywords = Column(Text, nullable=True)
```

キーワードはカンマ区切りの `Text` です。検索条件を別テーブルに正規化するのは、トピックごとに条件が増えてからで十分だと判断しました。

### 2. 鍵と接続先はサーバーに閉じる

```python
# backend/main.py
class Settings(BaseSettings):
    database_url: str = "sqlite:///./test.db"
    llm_model_name: str = "gpt-3.5-turbo"

    model_config = SettingsConfigDict(env_file='../.env', extra='ignore')
```

ブラウザには鍵を渡さず、`/config` は型名とモデル名だけを返します。収集と要約をサーバーに置く設計では、この線引きがそのまま安全境界になります。

### 3. 出力の形を先に決めておく

`/digest/{topic_id}` は現時点ではダミーですが、返す形は決まっています。

```python
# backend/main.py
return {
    "topic_id": topic_id,
    "generated_at": "2023-10-27T10:00:00Z",
    "summary": "LLMs continue to advance rapidly. ...",
    "key_tweets": [{"id": "12345", "text": "...", "author": "userA"}],
}
```

形を先に固定すると、UI と要約処理を別々に進められます。中身がダミーでも、インターフェースが決まっていれば画面は作れます。

## 結果

開発中なので、利用者数や削減時間の数値はありません。現時点で言えるのは定性の範囲です。

- 読む前の探索が「キーワード登録」に置き換わる
- 読む量はダイジェストの長さで決まり、タイムラインの流れに左右されない
- 読んだ後の整理を、要約という形でサーバーが持つ

| 工程 | Before | After（設計上） |
|---|---|---|
| 探索 | タイムラインを開いて目で拾う | 登録済みの条件で収集する |
| 読み込み | 投稿とスレッドを追う | 要約と主要投稿だけを読む |
| 整理 | 頭の中でまとめる | ダイジェストとして保存し、再閲覧する |

After は設計上の到達点です。収集と要約が入るまでは、この列は埋まりません。

## 向かないケース・残課題

- **速報を追いたい場合**: 収集の間隔次第で遅れます。リアルタイム性が要るなら別の手段が必要です。
- **原文のニュアンスを確認したい場合**: 要約は圧縮なので、引用や反論の文脈は落ちます。`key_tweets` から原文へ戻れる設計にしておきたいところです。
- **投稿が集まらないテーマ**: ニッチすぎるとダイジェストが空になります。何件あれば要約するかの閾値設計が要ります。
- **X API への依存**: 仕様や利用枠の変更で収集が止まります。クライアントを差し替えられる形にしておく必要があります。
- **認証が無い**: 現状は誰のトピックかを区別しません。複数人で使うなら認証が前提になります。
- **マイグレーション未導入**: Alembic が無いため、テーブル変更の履歴を残せません。

## まとめ

- 読む時間を増やすのではなく、読む前後の工程をサーバーへ移す
- 関心をデータにすると、収集も要約も自動化の対象になる
- 出力の形を先に決めると、中身がダミーでも UI と処理を並行できる

現状は器だけで、ダイジェストの中身はまだ空です。それでも「何を読むかを決めてから読む」という形は、収集と要約を足す前後で変わりません。
