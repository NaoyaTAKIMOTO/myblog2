## 執事に商品を勧めさせると、執事じゃなくなる

LINE で動く会話ボットを作るとき、最初にぶつかるのは「続かない」という問題です。キャラクターを立てると最初の数回は楽しいのですが、会話がパターン化して数日で開かれなくなります。そこで商品提案を足すと、今度は会話の途中で唐突にリンクが貼られ、執事が営業マンに変わります。

**Turtle Butler（カメ執事）** は、この2つを同時に満たそうとした LINE ボットです。落ち着いた関西弁の執事として振る舞い、相手の名前や好みを覚え、話が商品に向いたときだけ楽天の商品を勧めます。実装は TypeScript と Gemini、記憶は Firebase Realtime Database、商品検索は楽天の API を MCP サーバー越しに呼びます。

この記事では、キャラクター性と提案をどう住み分けたか、どこで妥協したかを書きます。

## 既存手段の限界

| 手段 | できること | 限界 |
|---|---|---|
| 固定応答の分岐 | 速く、安く、暴走しない | 同じ返事が返る。話題が続かない |
| プロンプトに商品リンクを埋め込む | 実装は数行 | 価格も在庫も古くなる。文脈と無関係な提案になる |
| すべてを1回の LLM 呼び出しに任せる | 文章は自然 | 存在しない URL を作る。価格を捏造する |
| 汎用のチャット UI を使う | 高機能 | LINE の友だち導線に乗らない |

1番目は「飽きる」、3番目は「嘘をつく」という別の壊れ方をします。カメ執事が避けたかったのは両方でした。

設計の判断は3つです。

- **話し方はプロンプト、品揃えは API**: 人格は `src/prompts.ts` の定数に閉じ込め、商品の事実は楽天 API の応答からしか取らない
- **提案の可否はモデルに任せる**: コードで「この語が出たら提案」と書かず、関数呼び出しの判断を Gemini に委ねる
- **記憶は渡す量を絞る**: 生の履歴は直近2件だけ。長期は要約と最近の話題5件に圧縮する

トレードオフもあります。判断をモデルに任せると、**提案しないターンが出ます**。確実に提案させたいときのために「楽天で検索」「商品を探して」といったウェイクワードをプロンプトに用意しました。逆に、毎回必ず提案させると執事の口調が壊れるので、あえて確率を上げていません。「静かな接客」を優先した設計です。

## 実装の要点

### 1. 人格プロンプトに「禁止事項」を書く

人格は `src/prompts.ts` の `BASE_SYSTEM_PROMPT` 1つです。ここには性格と言葉遣いだけでなく、**やってはいけないこと**を明示しています。

```ts
// src/prompts.ts（BASE_SYSTEM_PROMPT の抜粋）
【商品提案の振る舞い】
以下の場合に楽天の検索ツール（search_rakuten_items）を使って商品を検索し、
そのリンクを穏やかに提案します：
1. ユーザーが商品について直接尋ねた場合
2. 「楽天で検索」「商品を探して」「おすすめを教えて」などのウェイクアップワードを使った場合
3. ユーザーの感情や会話履歴から、気分転換や興味を引く商品が適切だと判断した場合

【禁止事項】私を急かしたり、プレッシャーをかけること。
ネガティブな話題に深く入り込むこと。キツいユーモアや不快な言葉遣い。
専門的なアドバイス。キャラクター設定を破る発言（例：「私はAIです」）。
```

効いたのは禁止事項のほうでした。人格が壊れる典型は、AI であることを認める、専門的な助言を始める、急かす、の3つです。商品提案という「営業の機能」を足すと、この3つが一気に出やすくなります。禁止を文章で固定しておくと、機能を足しても口調が戻ります。

### 2. 記憶を3層に分けて、渡す量を絞る

記憶は RTDB に置き、リクエストのたびに読み直します。保存するのは名前・好み・感情・最近の話題・会話履歴・要約です。ただし Gemini に渡すのは一部だけです。

```ts
// src/kame_buttler.ts（handleLineRequest）
userInfo.recentTopics.push(userMessage);
if (userInfo.recentTopics.length > 5) {
  userInfo.recentTopics.shift(); // 古い話題は捨てる
}

if (userInfo.chatHistory.length % 10 === 0) {
  userInfo.chatSummary = await summarizeChatHistory(userInfo.chatHistory);
  userInfo.chatHistory = []; // 要約したら生ログは消す
}
```

3層は「直近2件の生ログ」「10往復ごとの要約」「最近の話題5件と好み」です。生ログを全部渡すと、過去の話題に引っ張られて今の一言への返事が薄くなります。逆に要約だけだと、直前の一言の温度が消えます。直近だけ生で、それ以外は圧縮、という分担にしました。

好みの抽出は LLM に任せず、「名前は」「好きな食べ物は」で始まる発言を定型で拾います（`updateUserName` など）。ここは外すと記憶が壊れるので、確実に動く方を選びました。

### 3. 商品はモデルに書かせず、API から返す

URL をモデルに書かせると、存在しないリンクや古い価格が返ります。そこでキーワードだけ作らせ、商品は API の応答から取ります。

```ts
// src/kame_buttler.ts（getGeminiResponse）
if (functionCall.name === 'search_rakuten_items') {
  const products = await callMcpTool('rakuten-server', 'search_rakuten_items', {
    keyword: args.keyword,
    hits: args.hits
  });
  return JSON.stringify({
    tool_code: {
      name: 'search_rakuten_items',
      result: JSON.stringify(products)
    }
  });
}
```

`hits` は受け側の `apps/rakuten-server/src/index.ts` が `Math.min(args.hits || 5, 30)` で丸めます。モデルが 100 件と言っても 30 件で止まるので、コストと待ち時間が暴走しません。

ただし、ここには未完成の部分があります。ツールの結果を Gemini に返して執事の口調で文章を作り直す往復が未実装で、現状は結果の JSON がそのまま返信になります。設計としては「事実は API、語りはモデル」で正しいのですが、最後の1往復が抜けています。

## 結果

リポジトリで確認できる範囲の変化です。

- 会話の入口で好みを宣言しなくても、「名前は」「好きな食べ物は」を含む発言から自然に記憶されます
- 商品提案がコードの分岐からプロンプトの判断に移り、会話の流れで出るようになりました
- RTDB のルールでデータの形を強制しています。会話履歴は100件まで、最近の話題は5件まで、`language` は4つの方言のみ、`sentiment` は5値のみ
- テストは単体27件・統合23件・E2E 9件、MCP サービス側に7件と5件。人格と記憶の回帰は単体と統合で拾えます

正直に書くと、ユーザー数や継続率といった成果の計測値はリポジトリにありません。この記事で言えるのは「設計として両立の形ができた」ところまでです。

## 向かないケース・残課題

- **常に売り込みたい用途**: 提案しないターンがある設計なので、商品提案が主目的のボットには向きません
- **ツール結果の往復**: 上に書いたとおり、関数呼び出しが起きたときの返信が人格を通りません。ここを直すのが最優先です
- **スタンプの感情**: 現状はパッケージ ID とスタンプ ID の固定マップ（約20件）で判定し、未知は `neutral` です。Gemini Vision による画像認識は docs で計画中と書かれている段階で、実装はまだです
- **感情分析の粒度**: キーワードマッチの4分類です。皮肉や複雑な感情は拾えません
- **保存の順序**: 感情分析が保存の後に走るため、その発言の感情は次回保存されます。1ターン遅れます

「静かな接客」が欲しい用途には向いていますが、即時性の高いセールスには別の設計が要ります。

## まとめ

キャラクターと提案の両立は、機能を足す問題ではなく、**置き場所を分ける**問題でした。

- 話し方はプロンプトに閉じ込め、禁止事項で守る
- 品揃えと価格は API に持たせ、モデルには触らせない
- 提案するかどうかはモデルに任せ、確実にしたいときはウェイクワードを用意する
- 記憶は渡す量を絞る。直近は生で、長期は要約で

この4点は、LINE に限らず「人格 + 外部データ」のボットなら同じように使えます。
