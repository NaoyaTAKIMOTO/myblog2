## 描いた直後に、誰にも聞けない

デッサンを独学で続けていると、いちばん困るのは「今の1枚が先週より良くなったのか」を判断できないことです。1枚描くのに、それなりの時間と集中力を使います。教室に通っていれば週に1回は見てもらえますが、家で1人で描いている夜の時間帯に、隣に講師はいません。

代わりの手段はいくつかあります。SNS に上げて感想をもらう、添削サービスに送る、あるいはクラウドの画像解析 API を使う。どれも「絵を外に出す」ことが前提になっていて、練習中のラフや模写を気軽に上げづらいという声をよく聞きます。著作権が気になる資料を模写している場合なら、なおさらです。

**デッサン先生（dessan-sensei）** は、この2つ——添削の相手がいないこと、絵を外に出したくないこと——を同時に外すために作りました。写真を撮って送ると、6項目を10点満点で採点し、総評と「次に練習するならこれ」まで返します。推論も保存も、すべて手元の Mac の中で完結します。

## 既存手段の限界

| 手段 | できること | 限界 |
|---|---|---|
| 美術教室・講師 | 的確な指摘と実演 | 頻度と費用。自宅で1人で描く時間にはいない |
| SNS の添削依頼 | 人が見てくれる | 公開が前提。返答までの時間。指摘の粒度がばらつく |
| クラウド VLM API | 24時間すぐ返る | 絵を外部に送る。従量課金。オフラインでは使えない |
| 独学の自己評価 | 追加コストなし | 自分の盲点は自分では見えない。上達の記録も残らない |

どれも間違った手段ではありません。ただ、この4つを並べると「外部に送らず、その場で、記録が残る」を満たすものがありません。デッサン先生はここを狙いました。

設計の決定は3つです。

- **推論を LAN の外に出さない**: Ollama を Mac 上で動かし、Go サーバーは同じマシンの :11434 に投げる
- **出力の形を固定する**: 点数・総評・最重要の改善点・次の練習の4点セットに絞る
- **文脈はテキストで渡す**: 過去の添削は画像ではなく、日付・平均点・改善ポイントの要約だけをプロンプトに入れる

3つ目はトレードオフの塊です。過去の画像も一緒に送ればモデルは比較しやすいかもしれませんが、そのぶんトークンと待ち時間が増えます。docs/adr/0002-learning-focused-design.md では、画像付きの会話履歴を「コンテキスト爆発」で却下し、RAG も「個人利用ではオーバーエンジニアリング」として捨てています。代わりに、直近のスコアと指摘だけをテキストで混ぜる方式を取りました。

もう1つのトレードオフが、認証を持たないことです。サーバーは `0.0.0.0:8080` で待ち受けますが、ログインもユーザー管理もありません。これは「1人用」「自宅の LAN 内」に振り切った結果で、その代わりに外出先からは使えません。

## 実装の要点

### 1. 添削の文脈は「直近5件のテキスト要約」

添削を実行するとき、サーバーは直近5件の要約を取ってプロンプトに差し込みます。

```go
// internal/handler/critique_handler.go
history, _ := h.critiques.RecentSummaries(r.Context(), 5)

vlmReq := domain.CritiqueRequest{
    ImageBytes: imageBytes,
    Items:      criteriaSet.Items,
    Level:      level,
    History:    history,
}
```

要約は SQL 1本で作ります。スコアを平均し、前回の改善ポイントを拾うだけです。

```go
// internal/store/critique_store.go（RecentSummaries）
SELECT c.created_at, COALESCE(AVG(s.value), 0), COALESCE(c.improvement, '')
FROM critiques c
LEFT JOIN scores s ON s.critique_id = c.id
GROUP BY c.id
ORDER BY c.created_at DESC
LIMIT ?
```

画像は今回の1枚だけなので、履歴が5件に増えてもリクエストは重くなりません。そのぶんモデルは「前回は陰影が課題だった」という文脈を持った状態で今回の絵を見ます。プロンプト側では、履歴がある場合に「前回からの変化を具体的に指摘してください」と指示し、初回だけは「基本的な良い点を見つけて褒めてください」に切り替えます（internal/ollama/prompt.go）。

### 2. レベルで指摘の量を変える

同じ絵でも、初心者に改善点を5つ並べると折れます。そこでレベルを3段階に分け、指摘の数と語彙を変えています。

```go
// internal/ollama/prompt.go
var levelDescriptions = map[string]string{
    "beginner": `初心者です。
- 良い点を最初にしっかり褒めてください
- 改善点は最も効果的な1点に絞ってください
- 専門用語は使わず、わかりやすい言葉で説明してください
- 励ましの言葉を添えてください`,
    // intermediate / advanced も同様に定義
}
```

初級者は改善点1点、中級者は1〜2点、上級者は2〜3点。画面側のセレクトボックスで選んだ値が、そのまま `level` として POST されます（web/src/features/critique/CritiquePage.tsx）。サーバーは未指定なら `beginner` に倒します。

### 3. 評価軸はコードではなくデータにする

初期状態では6項目が入っています。プロポーション、陰影・トーン、構図、線の質、立体感、全体の完成度です（internal/store/seed.go）。これはマイグレーション後の起動時に、まだ1件も評価軸がなければ投入されます。

```go
// internal/store/seed.go（抜粋）
{Key: "proportion", Label: "プロポーション", Description: "対象の形状・比率の正確さ"},
{Key: "shading", Label: "陰影・トーン", Description: "光源を意識した明暗表現、グラデーションの滑らかさ"},
{Key: "composition", Label: "構図", Description: "画面内の配置とバランス、余白の使い方"},
```

項目は Web UI から増減できます。API を直接叩くなら次の1行です。

```bash
curl -s -X POST http://localhost:8080/api/criteria \
  -H 'Content-Type: application/json' \
  -d '{"name":"クロッキー用","items":[{"key":"gesture","label":"動きの勢い","description":"ポーズの流れが伝わるか"}]}'
```

評価軸を変えると、次回のプロンプトに渡す項目も JSON の雛形も自動で変わります。プロンプトに項目を直書きしていないため、コードを触らずに「今日は手のクロッキーだけ見てほしい」といった使い方ができます。

## 結果

- 添削は6項目×10点満点。総評、最重要の改善点、次の練習テーマが1回で返ります
- 履歴は自動で溜まり、一覧・詳細・削除ができます。直近5件は次回の添削の文脈として使われます
- アップロードは20MBまで、JPEG と PNG に対応します
- 推論も保存も Mac 内で完結し、外部への送信はありません。API の従量課金も発生しません
- iPad の共有シートから画像を渡せるよう、PWA の共有ターゲットを定義しています（web/public/manifest.json と web/public/sw.js）

体感として大きいのは、返答を待つ間に「次はどこを見るか」が決まることです。点数が低い項目が1つに絞られ、そこに対する練習方法まで書いてあるので、次の1枚の目的がはっきりします。教室までの1週間が、空白ではなくなります。

## 向かないケース・残課題

- **複数人・外出先**: 認証がなく、LAN 内からのアクセスを前提にしています。外に公開するなら、認証と HTTPS は必須です
- **HEIC のままの写真**: 受け付けるのは JPEG と PNG だけです（internal/handler/critique_handler.go）。iPad の設定によっては共有時に変換が必要になります
- **判定の精度**: 点数はモデルの能力に依存します。絶対値として読むより、同じ評価軸での推移として読むほうが実用的です
- **添削箇所を囲む表示**: README の機能一覧には「添削箇所のハイライト、四角や丸で囲む」とありますが、現時点のコードには該当する実装が見当たりません。これからの部分です
- **配布**: `make build` のバイナリは API のみを返し、画面は Vite の dev server 前提です。SPA の同梱は README でも未対応と書かれています

「1人で、家で、絵を外に出さずに、その場で感想がほしい」という条件には合います。逆に、複数人で使う、外出先から使う、判定の厳密さを求める、という用途には向きません。

## まとめ

- 添削の相手がいない壁は「ローカル VLM + 評価軸の固定」で外す
- 絵を外に出したくない壁は「推論も保存も同じマシン」で外す
- 続かない壁は「履歴をテキストで文脈に入れる」で外す

3つとも、特別なサービスを足すのではなく、処理をどこに置くかを決めただけで解けました。同じ考え方は、日記の添削でも、写真の構図チェックでも使えます。
