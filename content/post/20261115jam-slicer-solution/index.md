## 分割作業のどこが苦痛か

配信のアーカイブを曲ごとに分けたいだけなのに、やることは多いものです。

1. プレイヤーで頭から再生し、曲の始まりと終わりを耳で探す
2. 時刻をメモして、動画編集ソフトに打ち直す
3. 書き出しを待つ
4. 曲数ぶん繰り返す

曲が10曲あれば、この往復が10回。途中で1箇所でも時刻を間違えると、その区間だけやり直しになります。

JamSlicer は、この作業を「アップロード → しきい値の調整 → 一括切り出し」の3ステップに置き換えます。ここでは、実際にぶつかった3つの壁と、その外し方を書きます。

## 既存手段の限界

| 手段 | できること | 限界 |
|---|---|---|
| 動画編集ソフトで手作業 | 自由な位置で切れる | 曲数に比例して時間がかかる。時刻の記録と入力が二度手間 |
| Python で librosa / moviepy | 無音検出を自動化できる | 音声を配列に読み込むため、1GB の動画で 5〜10GB のメモリを使う |
| FFmpeg を直接叩く | 高速・低メモリ | 毎回コマンドを組み立てる必要があり、区切りの確認ができない |

JamSlicer が狙ったのは、3番目の速さと1番目の確認しやすさを両立させることでした。

設計の要点は3つです。

- **解析は1回だけ**: アップロード時に音量カーブを取り、以降はそのデータを使い回す
- **調整はブラウザ**: しきい値を変えても再解析しない
- **切り出しはコピー**: 再エンコードせず、画質と時間を守る

区切りの確認と調整をブラウザに置いたことで、「自動検出の結果をその場で直せる」ようになりました。完全自動にしなかったのは、無音の長さも音量も動画ごとに違うためです。

## 実装の要点

### 解析: 音量カーブを取る

`POST /analyze-volume` に動画を送ると、0.5秒間隔の音量データと、推奨しきい値が返ります。推奨値は平均音量と標準偏差から計算しています。

```bash
curl -X POST http://localhost:8000/analyze-volume \
  -F "file=@live.mp4"
```

### 調整: 区間はクライアントで作る

返ってきた音量データから、ブラウザ側の `detectSilence` が無音区間を求め、`calculateSegments` が音楽区間を組み立てます。最小無音長は1.0秒、サンプリング間隔は0.5秒です。

```ts
// frontend/src/segmentCalculator.ts
const isSilent = point.volume < threshold;
```

しきい値を下げれば区間は長く、上げれば短くなります。この試行錯誤が通信なしでできることが、使い勝手の中心です。

### 切り出し: 確定した区間だけを送る

区間が決まったら `POST /cut-simple` に JSON で送ります。

```bash
curl -X POST http://localhost:8000/cut-simple \
  -F "file=@live.mp4" \
  -F 'segments=[{"start":0,"end":45.2,"duration":45.2}]'
```

サーバーは各区間を `-c copy` で切り出し、ZIP にまとめてダウンロードURLを返します。2秒未満の区間はノイズとみなして捨てています。

### 片付けとダウンロード

切り出したファイルはサーバーの一時ディレクトリに置かれ、ZIP にまとめてから `/download-segments/{zip_filename}` で配信されます。アップロードした動画の一時ファイルは処理の最後に削除されるため、ディスクに残り続けることはありません。

```python
# backend/main.py（cut_simple）
output_dir = tempfile.mkdtemp()
...
"download_path": f"/download-segments/{os.path.basename(zip_path)}"
```

分割結果をDBに保存しない設計なので、「まず試して、違えばしきい値を変えてもう一度」という使い方が気軽にできます。

## 結果

README に記録されている従来実装との比較です。

| 項目 | 従来版 (librosa/moviepy) | JamSlicer |
|---|---|---|
| メモリ使用量 | 5〜10GB | 30〜50MB |
| 音量解析速度 | 基準 | 2〜5倍高速 |
| 動画分割速度 | 基準 | 10〜20倍高速 |

作業としては、曲ごとの時刻メモと編集ソフトへの打ち直しがなくなり、確認と調整だけが残ります。分割そのものはストリームコピーなので、待ち時間はほぼファイルコピーの時間です。

### 実行コスト

CPU を使うのは解析の1回だけで、FFmpeg が音声トラックを1度デコードします。その後にやり取りするのは数百KBのJSONです。切り出しはストリームのコピーなので I/O が中心になります。GPU は不要で、ノートPCでも小さなVPSでも動きます。

## 向かないケース・残課題

- **無音が短い動画**: ライブのように曲間の拍手が続く場合、無音区間が1秒未満だと検出できません。しきい値を上げても区切りが曖昧になります。
- **BGM が流れ続ける動画**: 曲間にも音が乗るため、無音検出そのものが使えません。
- **厳密な頭出し**: `-c copy` はキーフレーム単位で切るため、狙った位置と数フレームずれることがあります。厳密に合わせたい場合は再エンコードが必要です。
- **正規化**: コードには YouTube 向けのラウドネス正規化（-14 LUFS）のオプションがありますが、UI からは未公開です。

「無音で区切れる素材」に限定すれば強い、というのが現時点の結論です。逆に、区切りが音の変化で決まる素材には、別の検出手法が必要になります。

## まとめ

- 手作業の壁は「確認しながら自動化する」ことで外す（完全自動にしない）
- メモリの壁は「FFmpeg に任せて配列を作らない」ことで外す
- 速度の壁は「再エンコードしない」ことで外す

3つとも、特別なライブラリではなく、処理の置き場所を変えることで解けました。
