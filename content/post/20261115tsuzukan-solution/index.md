## 「続きが出てた」に、あとから気づく

買い忘れは、たいてい本屋で起きます。平積みされた新刊を見て「あ、この作品の前の巻、家にあるのに次の巻を買っていない」と気づく。あるいは Amazon のおすすめで見かけて、ようやく思い出す。思い出せたのは偶然で、仕組みではありません。

厄介なのは、買い忘れが「どの作品の、何巻まで持っているか」という状態の管理に帰着することです。タイトルは覚えていても、最新巻が何巻かは覚えていません。シリーズが10あれば、10個の状態を頭で持つことになります。

tsuzukan は、この状態を外部に預けるためのアプリです。本のバーコードをスマホで読み取るか、Amazon・楽天の購入履歴CSVを取り込むと、ISBN から書誌を引き、シリーズと巻数を判定して登録します。あとは新刊チェックを実行すると、未所持の巻が一覧で出て、Amazon／楽天のリンクからそのまま購入できます。

この記事では、何が難しくて、どう設計したかを書きます。

## 既存手段の限界

| 手段 | できること | 限界 |
|---|---|---|
| 出版社・書店のメールマガジン | 新刊の発売を知らせる | 登録した著者・レーベル単位。手持ちの巻との突き合わせは人がやる |
| Amazon のほしい物リスト | 商品を溜めておける | 買った巻を手で外す必要がある。続刊の自動追加はない |
| 表計算ソフトで管理 | 自由に項目を設計できる | 巻数の判定、書影、購入リンクを全部自前で埋めることになる |
| カレンダーに発売日を書く | 日付で通知できる | 発売日を調べて転記する作業が発生する。刊行がずれると破綻する |

共通するのは「状態を人が持つ」前提です。どの手段も、記録の更新を人が忘れないことを要求します。買い忘れる人が、記録の更新だけは忘れない、という仮定が無理があります。

## 解決の設計

やることを3つに絞りました。

1. **登録は「持っている本」だけ**。新刊を先回りして登録するのではなく、手元の巻を登録する
2. **シリーズと巻数は機械が判定する**。タイトルから `(1)` `第1巻` `Vol.1` などを抽出する
3. **新刊はシリーズ単位で引く**。著者名とシリーズ名で検索し、未所持の巻だけを残す

設計上のトレードオフは3つあります。

- **完全自動にしない**: 新刊チェックはユーザーが実行する。定期実行にすると、外部APIの失敗やレート制限が黙って溜まる
- **書誌は共有、状態は個人**: 本の情報（`books` / `series`）は全ユーザーで共有し、所有・設定・チェック時刻は per-user 表に置く。同じISBNを何度も引かない
- **判定できないものは人に決めさせる**: 巻のタイトルが共通しない作品は、機械には判定できない。手動モードで紐付けてもらう

3つ目が、この設計でいちばん効いています。詳しくは実装の要点で触れます。

## 実装の要点

### 登録: ISBNを起点にする

登録は `POST /api/v1/books` に ISBN を送るだけです。バーコードスキャンもCSV取り込みも、最終的にこの形に落ちます。

```bash
curl -X POST http://localhost:8080/api/v1/books \
  -H "Content-Type: application/json" \
  -d '{"isbn": "9784088820774"}'
```

サーバーは openBD に書誌を聞き、無ければ NDLサーチ → 楽天Books の順にフォールバックします。ISBN が同じなら同じ本なので、`books` は共有カタログとして1行だけ持ちます。

購入履歴の取り込みは、Amazon の `Retail.OrderHistory.3.csv`（物理商品）と `Digital Items.csv`（Kindleなど）に対応しています。行ごとに ASIN やタイトルから ISBN を探して登録するため、すべての商品が登録されるわけではありません。この制約はREADMEにも明記しています。

### 判定: タイトルからシリーズと巻数を抜く

`internal/transform/text.go` の `ExtractSeriesInfo` が、タイトルを正規化してから正規表現で巻数を探します。

```go
// internal/transform/text.go（ExtractSeriesInfo より抜粋）
candidate := stripTrailingEditionLabel(stripTrailingLabels(StripWaveDashSubtitle(title)))

for _, pattern := range reVolumePatterns {
	matches := pattern.re.FindStringSubmatch(candidate)
	if len(matches) < 3 {
		continue
	}
	volume, err := strconv.Atoi(toASCIIDigits(matches[2]))
	if err != nil || volume <= 0 {
		continue
	}
	if !pattern.marked && volume > maxPlausibleVolume {
		continue
	}
	return trimSeriesNameTrailingPunctuation(matches[1]), &volume
}
```

出版社ラベルや副題を先に落とすのが順序として重要です。落とさずに巻数を探すと、副題の後ろにある数字を拾ったり、シリーズ名が販促タイトル全体になったりします。

### 追跡: 探せないシリーズは「探さない」

新刊チェックは、シリーズごとに書誌検索をかけ、所有済みのISBNと巻数を除いた残りを新刊として返します。ただし、これが通用しない作品があります。巻のタイトルが共通しない続き物です。綾辻行人の館シリーズ、森博嗣の S&M シリーズのように、巻ごとにタイトルがまったく違う場合、タイトル検索でも著者検索でも他の作品が混ざります。

外部データでも決められません。openBD と NDL のシリーズ項目はレーベル名で、100冊のサンプルで作品名を持っていたのは0冊でした。そこで `detection_mode = 'manual'` を用意し、ユーザーが紐付けた巻をシリーズの定義として扱います。チェックは外部に問い合わせず、紐付いた巻のうち未所有のものをそのまま返します。

```go
// internal/service/release.go（checkSingleSeriesNew より抜粋）
if series.DetectionMode == model.DetectionModeManual {
	return s.checkManualSeries(userID, series)
}
```

手動モードの分岐をキャッシュ判定より前に置いているのも意図的です。キャッシュは「最後に楽天へ聞いた時刻」を記録するもので、タイトル一致で動いていた頃の時刻が残っていると、コストのかからないチェックが飛ばされます。

### 購入: リンクはISBNから組み立てる

新刊一覧の各カードには、Amazon と楽天のリンクが付きます。Amazon は商品ページ（`/dp/<ASIN>`）で、ISBN-13 を ISBN-10 に変換して ASIN にします。楽天は商品IDを持たないため検索URLです。どちらもAPIを呼ばずに組み立てるので、一覧表示で外部APIを消費しません。

Amazon の商品ページが消えた本については、リンクを出さない処理を入れています（`books.amazon_available`、migration `000046`）。切れたリンクを踏ませるより、出さないほうが親切だと判断しました。

## 結果

作業として残るのは、登録といちどきりのチェックだけになります。曲ごとの時刻メモに相当する「巻数を数える」作業は、シリーズ判定に置き換わりました。

数字で確認できる範囲を挙げます。

| 項目 | 値 | 出典 |
|---|---|---|
| NDLサーチが返した所蔵カバー率 | 100冊のサンプルで97% | `cmd/server/main.go` のコメント |
| シリーズ名で聞いたときの既所有巻の再現率 | 91% | 同上 |
| 新刊チェックのキャッシュ | 既定24時間 | `config/config.go` |
| 新刊959件をシリーズ最新刊に集約 | 75枚のカード | `docs/new-release-covers.md` |

新刊一覧は、以前は1件1枚のカードでした。同じシリーズの3巻が並ぶこともあり、どの作品の新刊か分かりにくかったため、シリーズごとに最新刊1枚へ集約し、隠れた巻は「他N冊」としてシリーズ詳細へのリンクで辿れるようにしています。959件が75枚になったのは、その集約の結果です。

## 向かないケース・残課題

- **巻数のない本**: 画集や単発の小説は、そもそも「続刊」がありません。シリーズ判定に失敗すると未割り当ての書籍として残るため、手で整理する必要があります。READMEにも、シリーズに紐づかない書籍が6冊あったことが記録されています。
- **電子と紙の混在**: 同じ巻を紙と電子の両方で持つ場合、所有の記録が二重になりえます。エディション単位の記録は用意していますが、運用でカバーしている部分があります。
- **楽天APIのIP制限**: 楽天のアプリはVPSの送信元IPのみ許可しており、ローカル開発では 403 `CLIENT_IP_NOT_ALLOWED` になります。その場合は NDL にフォールバックしますが、書影は取れません。
- **NDLの同時接続**: NDL は同時アクセス数に上限があり、429 を返します。クライアント側で同時1リクエストに制限しています。
- **発売日の通知**: 現在は「新刊が出たか」を引く仕組みで、発売前の予約を促す通知はありません。発売日を未来日で保持する設計にはなっていません。

「手持ちの巻がはっきりしている作品」には強い、というのが現時点の結論です。逆に、巻の概念がない本や、タイトルが毎回変わる作品は、人の判断が必要になります。

## まとめ

- 買い忘れは記憶力ではなく、状態の置き場所の問題。人は「持っている本を登録する」ことだけ担当する
- 判定できるものは機械に、できないものは人に決めさせる。手動モードを用意したことで、タイトルが共通しない作品も同じ画面で扱える
- 書誌は共有、状態は個人。同じISBNを何度も引かない構造が、外部APIの呼び出しを抑える
- 探せないものは探さない。外部に問い合わせない経路を設計に持つと、障害点が減る
