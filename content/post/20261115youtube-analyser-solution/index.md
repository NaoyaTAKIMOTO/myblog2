## 再生数ランキングを見ても企画が決まらない

企画会議で「いまバズっている動画」を共有するとき、YouTube の急上昇タブをそのまま開くことが多いと思います。ただ、そこに並んでいるのは登録者数が何十万というチャンネルの動画です。再生数順に並べ替えても結果は同じで、上位は大きなチャンネルが占めます。

知りたいのは「大きな数字」ではなく「自分たちと同じ規模のチャンネルが、どこまで伸びたのか」です。ところが急上昇タブにも再生数順にも、規模を補正する仕組みはありません。結果として会議では数字の大きさだけが共有され、「なぜ伸びたのか」の議論に進めません。

この記事では、規模を揃えて比べるために何を画面に置き、どう実装したかを書きます。

## 既存手段の限界

| 手段 | できること | 限界 |
|---|---|---|
| YouTube の急上昇タブ | いま伸びている動画が分かる | 日本全体の大型チャンネルが中心。規模の補正がない |
| 再生数順のソート | 数字の大きい順に見られる | 大手が上位を占め、小規模の当たりが埋もれる |
| 手元のスプレッドシート | 自由に計算できる | 動画ごとに登録者数を調べる手間で更新が止まる |
| 登録者数で絞り込む | 比較する母集団を揃えられる | 「その中でどれが当たったか」は別に比べる必要がある |

4番目の方向は正しいのですが、絞り込んだあとに「規模に対してどれが伸びたか」を示す列がありません。揃える手段と比べる手段が別々になっているのが、手作業が続く原因でした。実際、表を手で作るときに一番時間を使うのは計算ではなく、動画ごとにチャンネルを開いて登録者数を写す作業です。ここが自動化されない限り、表は数週間で更新されなくなります。

## 解決の設計

置く数字を3つに絞り、同じ画面に並べることにしました。

- **バイラル係数**（再生数 ÷ 登録者数）: 規模の補正。1つの数字で順位が決まる
- **中央値**: 外れ値に強い代表値。平均と並べて初めて分布が見える
- **エンゲージメント率**（(いいね＋コメント) ÷ 再生数）: 見られ方の質。再生数が伸びても反応が薄い動画を切り分ける

設計上のトレードオフは2つあります。

1つは、係数が1つの数字で強いぶん、母数が小さいと1本の外れ値で跳ねることです。だから中央値と ENG 率を併記し、係数だけで判断しない形にしました。もう1つは、完全に自動で「当たり」を判定しないことです。何を当たりと見なすかは企画の目的で変わるため、最後は人が読む前提にしています。

複合スコア（係数と ENG 率を重み付けして1つにする）も検討しましたが、重みの根拠を説明できないためやめました。指標を3つ並べ、どれを重視するかは読む側に委ねるほうが、企画の議論には使いやすいと判断しています。

## 実装の要点

### 規模で割る

係数は、動画詳細とチャンネル情報を突き合わせる場所で計算しています。

```ts
// src/lib/youtube/client.ts（calcStats）
const engagementRate = viewCount > 0 ? ((likeCount + commentCount) / viewCount) * 100 : 0

// src/lib/youtube/client.ts（buildVideoItems）
const subscriberCount = subscriberMap.get(item.snippet.channelId) ?? 0
const viralCoefficient =
  subscriberCount > 0 ? Math.round((stats.viewCount / subscriberCount) * 10) / 10 : 0
```

登録者数が 0 のときは割り算をせず 0 を返します。ゼロ除算を避けるためですが、この判断が後述の落とし穴になります。

### 分布の真ん中を見る

平均だけを見ていると、50件のうち1本が跳ねただけで全体の印象が変わります。そこで中央値も同じ配列から出し、最大値は再生数ではなく係数で選びます。

```ts
// src/lib/youtube/stats.ts
const sorted = [...viewCounts].sort((a, b) => a - b)
const mid = Math.floor(sorted.length / 2)
const medianViewCount =
  sorted.length % 2 === 0 ? (sorted[mid - 1] + sorted[mid]) / 2 : sorted[mid]

const topPerformer = videos.reduce((top, v) =>
  v.viralCoefficient > top.viralCoefficient ? v : top
)
```

### 比較する母集団を揃える

絞り込みはプリセットにしました。自由入力にすると、何を基準に揃えたのかが共有されないためです。

```tsx
// src/components/search/SearchForm.tsx
const SUBSCRIBER_MAX_PRESETS = [
  { label: '指定なし', max: undefined },
  { label: '〜1万', max: 10_000 },
  { label: '〜10万', max: 100_000 },
  { label: '〜100万', max: 1_000_000 },
] as const
```

選んだ上限は `subscriberCountMax` として API に渡り、`src/lib/youtube/client.ts` で登録者数が上限以下の動画だけに絞ってから、係数順に並べ替えます。絞り込みと並べ替えの順序が逆だと、上位50件を取ったあとに絞って件数が足りなくなるため、この順序は変えられません。

## 結果

同じ50件でも、再生数順と係数順では並びが変わります。会議で最初に見るものが「大きい数字」から「規模に対して伸びた動画」に変わり、そこから企画の理由を読む流れになりました。

サマリーに並べるのは、検索結果の件数・平均再生数・中央値再生数・平均 ENG 率・平均バイラル係数の5つです。これ以上増やさないのは、会議で最初に見る順番を固定するためです。指標が増えるほど、人は都合のよい数字を選んでしまいます。

もう1つ効いたのが、トレンド発掘モードの軽さです。`chart=mostPopular` と `regionCode=JP` で日本の急上昇を50件取り、`videos.list` と `channels.list` の2回で済みます。キーワード検索のように3ページ分の `search.list` を回さないため、クォータを気にせず何度でも試せます。

作業としては、動画ごとに登録者数を調べて表に入れる手間がなくなり、数字を読む時間だけが残ります。

## 向かないケース・残課題

- **登録者数が非公開のチャンネル**: `hiddenSubscriberCount` が true だと登録者数を 0 として扱うため、係数も 0 になり末尾に落ちます。「当たりがない」のか「数字が取れない」のかを画面で区別できていません。
- **登録者数は現在値**: 係数の分母は投稿時点の登録者数ではなく、取得時点の値です。動画がきっかけでチャンネルが伸びた場合、その動画の係数は過小に出ます。
- **投稿直後の動画**: 再生数が小さいうちは1再生の重みが大きく、係数が数倍単位でぶれます。期間フィルタで「今週」を選ぶと、この影響を強く受けます。
- **並び順の誤解**: UI の「並び順（取得時）」は候補の集め方を変えるだけで、表示は常に係数順です。
- **テスト**: テストは `subscriberCountMin` や `viewCountMin` を期待していますが、実装は `subscriberCountMax` までしか持っていません。執筆時点で `npm test` は51件中25件が失敗します。
- **期間の下限**: `publishedBefore` は API 側で受け取れますが、UI に入力の導線がありません。

## まとめ

- 規模の違う動画を並べても、順位に意味は出ない。まず母集団を揃える
- 揃えたら、割り算した指標（係数）と分布の代表値（中央値）を同じ画面に置く
- 1つの数字で断定せず、ENG 率のような別の軸を併記する
- 数字の限界（非公開・現在値・投稿直後）を画面の外でも説明できるようにしておく

特別な分析基盤は不要で、API を数回呼んで割り算を1回足すだけで、会議の議題は変わります。
