## 原典を探す作業は、検索エンジンを何個も開くことから始まる

自分の写真が、知らないアカウントに投稿されている。クレジットはない。元は自分だと示したいが、証拠が要る。あるいは、回ってきた画像の出どころを知りたい。

まず逆画像検索を使います。ところが検索エンジンは1つではありません。Yandex、TinEye、Google、Bing、イラストなら ascii2d や SauceNAO。同じ画像を入れても、返ってくる候補はまったく違います。結局こうなります。

1. 複数の検索エンジンに同じ画像を入れる
2. それぞれの候補一覧を開く
3. 候補ページを1件ずつ開いて公開日を見る
4. 同じ画像か、加工されていないかを目で比べる
5. 一番古そうなものをメモして、また次の候補へ

候補は数十件から数百件。1件あたり10秒でも、100件で15分以上かかります。しかも「一番上に出た候補」が原典とは限りません。検索結果は関連度順で、日付順ではないからです。

## 既存手段の限界

| 手段 | できること | 限界 |
|---|---|---|
| 逆画像検索を1つずつ使う | 候補は出る | エンジンごとに結果が違い、横断比較は手作業 |
| 検索結果の並び順 | 関連度の高い順に出る | 日付順ではない。古い転載が上に来るとは限らない |
| 候補ページの公開日 | そのページの日付が分かる | ページの日付は、載っている画像の日付とは限らない |
| 目視での画像比較 | トリミングや文字入れに気づける | 件数に比例して時間がかかる |

3番目は実際に罠でした。ページの公開日は、そのページの主画像のものです。関連画像として別の写真が載っているページでは、日付だけを見るとまったく違う画像の日付を拾ってしまいます。実際に、2021年の Tenor のページを原典と誤認していました。

設計の判断は3つです。

- **列挙はエンジンに任せる**: 候補を増やすのは各サービスの仕事です。自前で持つのは横断比較だけにしました
- **判定は機械、最後の判断は人**: 「同じ画像か」は照合で決めます。それが原典として妥当かは目で確認します
- **日時は根拠ごと持つ**: 投稿ID、ページ記載、アーカイブの保存日を区別したまま比較します

トレードオフも2つあります。1つは完全自動にしないこと。返すのは「候補のうち最古」であって、この世の最初の投稿とは限りません。もう1つは対象を絞ったことです。同一画像の初出だけを見て、同じ人物の別写真を探す用途は切り捨てました。NSFW 画像を扱う前提もあり、Google 系は主力にしていません。

## 実装の要点

### 入力を3種類に揃える

`uv run origin-finder` で `http://127.0.0.1:8765` が立ち上がります。

```bash
uv run origin-finder
curl -s -X POST http://127.0.0.1:8765/api/search -F "file=@image.jpg"
curl -s -X POST http://127.0.0.1:8765/api/search -F "url=https://x.com/<user>/status/<id>"
```

X の投稿URLを渡すと、FxTwitter API で添付画像を取り、その投稿自身も候補に加えます。Instagram と TikTok の URL は未対応で、画像を保存してアップロードする必要があります。

### 同じ画像かを3段で決める

全候補に重い照合はかけられません。サムネイルの pHash で確定するものを先に落とし、残りをサムネイルの特徴点で絞り、最後に上位40件だけ元画像を取り直して判定します。

```python
# src/origin_finder/matching.py
INLIERS_SAME_MIN = 18
COVERAGE_MIN = 0.15
PHOTOMETRIC_MIN = 0.7
```

インライア（位置合わせで対応が取れた特徴点）が18以上、一致範囲が15%以上、位置合わせ後の見た目が0.70以上。3つすべてを満たしたときだけ「同じ写真」とします。形が合うだけの別写真を通さないための条件です。

### 日時は「その時点で存在した証拠」として扱う

```python
# src/origin_finder/judge.py（judge の末尾）
eligible = [c for c in cands if c.date and is_match(c) and c.date_source != OTHER_IMAGE]
eligible.sort(key=lambda c: (effective_date(c), DATE_RANK.get(c.date_source, 9)))
origin = eligible[0] if eligible else None
```

日時の根拠は、X / TikTok / Instagram の投稿ID、ページ記載、TinEye のクロール日と Wayback 保存日です。原典を選ぶときは根拠の強さで足切りせず、最古を選びます。どの日時も「その時点で既に存在した」証拠だからです。日付しか分からないものは、その日の終わりとして比較します。

## 結果

`docs/plan.md` に記録された実測値です。

| 項目 | 値 |
|---|---|
| 検索1回の所要時間 | 15〜20秒（打ち切り時も約1分以内） |
| 重複統合（エッフェル塔） | 106ページ → 30グループ |
| 重複統合（シンク投稿） | 179ページ → 32グループ |
| 日付なしの同一写真（エッフェル塔） | 51件 → 40件 |

作業としては、5つの検索結果を開いて回る工程が、1回の検索と結果の確認に置き換わります。候補の一覧には「同じ写真」「同じ場面」「別の画像」の判定と日時の根拠が付いて出るので、どこから見るかで迷いません。

## 向かないケース・残課題

- **Instagram / TikTok の URL 入力**: 未対応です。正規の取得経路がないため、画像を保存してアップロードする運用にしています
- **Bing**: PicImageSearch 側の仕様追従が切れて常に失敗します
- **エンジンの得手不得手**: 実写は Yandex と TinEye が主で、ascii2d と SauceNAO はイラスト向けです
- **低テクスチャの自撮り**: 肌のように特徴点が少ない画像では、ORB の対応が取れず「別の画像」寄りになる可能性があります。精度不足なら SSCD を検討する、という段階です
- **見逃し**: 原典が検索結果に含まれなければ見つかりません。見逃し率はまだ評価していません

「検索結果に出てくる範囲で、最古の投稿を根拠付きで特定する」までが、現時点でできることです。

## まとめ

- 手作業の中心は「横断比較」と「日付確認」。前者は並列検索、後者は根拠付きの日時で畳む
- 自動化するのは判定まで。最後の判断は人に残す
- 「最古＝原典」は、日時の根拠の種類を区別して初めて成り立つ
