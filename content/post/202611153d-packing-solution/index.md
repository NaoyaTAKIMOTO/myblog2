## 朝の積み込みが、その日の午後を決めてしまう

宅配の朝は、荷台をできるだけ満杯にするところから始まります。1回で多く運べば便数が減り、車両も人も効率よく回るように見えるからです。

ところが満杯にするには、配達順を崩して詰め込む必要があります。後から届ける箱を手前に置き、先に届ける箱を奥や下に押し込む。すると配達先に着くたびに、目の前の箱をどかし、目的の箱を探し、また積み直すことになります。

この荷室作業（荷探し・荷室内の整理）は、拠点外の作業時間のうち約18%を占めるという調査があります。リポジトリの `docs/research.md` §7 が引用しているヤマト運輸の同行調査（2018年、約4,500件）です。拠点外の作業時間が8時間なら、1時間以上が荷物を動かすためだけに消えている計算になります。

**3d_packing** は、この「満杯にしない」判断を計画として出すツールです。守るのは最大積載量、天地無用、耐荷重、下からの支え、配達順に降ろせること、重心バランスの6つ。出力は3D表示だけでなく、箱に貼るA6ラベルとA4の積付け手順書まで含みます。

## 既存手段の限界

| 手段 | できること | 限界 |
|---|---|---|
| 経験と勘で積む | その場の荷物に柔軟に対応できる | 属人的で、配達順の制約は考慮されない。検証もできない |
| 3D CAD・積載シミュレータ | 寸法どおりに収まるかを確認できる | 配達順・耐荷重・支持率を同時に扱えず、作業手順までは出せない |
| 汎用のビンパッキング | 隙間なく詰める計画を出せる | 「隙間なく」が目的化し、現場のルールや降ろす順番を守れない |

調査では、Python で全制約を扱えるOSSが見つからなかったといいます（`docs/worklog.md`）。商用ツールにも、箱ごとの現場ラベルを出すものはありませんでした。そこで、計算エンジンは自前で書き、現場に渡す出力までを範囲にしました。

設計の要点は3つです。

- **配達順をハード制約にする**: 「後から届ける箱が、上または後扉との間にない」ことを、計画の必須条件にする
- **満杯を目的にしない**: 1便目に積む量を、配達順を守れる上限まで下げる。減らした分は2便目で運ぶ
- **現場に渡す形にする**: 積み順・置き場所・上にする面を、ラベルと手順書に落とす

トレードオフは便数です。1便目を減らせば2便目が必要になり、拠点に戻って積み直す往復が発生します。この往復が何分なら得か、という分かれ目も計算して出します。

## 実装の要点

### 1. 配達順をハード制約にする

配達順の判定は「後から届ける箱が、対象の箱の上にあるか、後扉との間にあるか」です。`src/packing/constraints.py` の `rehandles` がこれを数え、`validate_load` が `LIFO` の違反として報告します。

```python
# src/packing/constraints.py（rehandles）
above = xy & (arr[:, g.Z0] >= b[g.Z1])
door_side = yz & (arr[:, g.X0] >= b[g.X1])
blockers = np.nonzero(later & (above | door_side))[0]
```

ラストワンマイルのシーンでは `lifo=True` が設定され（`src/packing/presets.py`）、この条件が計画の必須条件になります。詰め込みの計画では、80箱のうち47箱が「どかす必要あり」と判定されました。提案手法では0箱です。

### 2. 満杯と配達順の両方をシミュレーションで比べる

効果は、1日の配達を丸ごとシミュレーションして測ります。積み方を変えた3通り（詰め込み／配達順どおり／配達順どおり＋不在への備え）を、同じ不在の抽選で回します。

```bash
uv run packing efficiency --mode multi --seed 0 --days 60 --out out/eff_multi
```

`--mode multi` は2便以上で回る運用、`--mode single` は1便の運用です。`--shares` で1便目に積む量の候補（既定は満杯の100%・90%・80%）を変えられます。詰め込みの計画は `lifo` を外し、不在への備えの重みも0にして作ります。

```python
# src/packing/efficiency.py（strategy_scene）
if strategy == "cram":
    return replace(scene, lifo=False, absence_weight=0.0)
if strategy == "ordered":
    return replace(scene, lifo=True, absence_weight=0.0)
if strategy == "robust":
    return replace(scene, lifo=True)
```

同じ荷物でも、制約の掛け方だけで「現状の積み方」と「提案する積み方」を並べて比べられます。

### 3. 積み方を現場の言葉に翻訳する

計画が良くても、積む人が再現できなければ意味がありません。`src/packing/instructions.py` は、箱ごとに「奥・中・手前」「左・中・右」「段」と、上にする面を出します。

```python
# src/packing/instructions.py（_load_steps）
code=f"L{li}-S{step_no:03d}-{DEPTH_CODE[di]}-{SIDE_CODE[si]}-{lv}",
position_ja=f"{DEPTH_JA[di]}・{SIDE_JA[si]}・{level_ja(lv)}",
face_up_ja=FACE_UP_JA[face],
```

位置コードは `L1-S003-B-L-1` のように、何号車の何番目・奥・左・1段目を表します。これがA6ラベル（QRコードつき）とA4手順書になり、3D表示と同じ計画データから作られます。

## 結果

`docs/benchmark.md` の計測（seed 0〜2、1日を40回シミュレーション）です。

| 運用（seed） | 現状（詰め込み満杯） | 最良の積み方 | 1日の短縮 |
|---|---|---|---|
| 2便以上 (0) | 173.3秒/個 | 配達順どおり＋不在への備え 144.3秒/個 | 61分 |
| 2便以上 (1) | 173.2秒/個 | 配達順どおり＋不在への備え 144.1秒/個 | 62分 |
| 2便以上 (2) | 169.6秒/個 | 配達順どおり＋不在への備え（74%）163.2秒/個 | 14分 |
| 1便 (0) | 151.3秒/個 | 詰め込み満杯 151.3秒/個 | 0分 |

2便以上で回る運用では、1個あたりの作業時間が173秒から144秒に下がり、1日あたり約1時間短くなります。荷室作業の割合は17%から1%へ下がります。これは1人1日あたり約20個多く配れること、または残業を1日1時間減らせることに相当します。乱数の種3つすべてで短縮し、seed 2 は配達順どおりだと3便目が必要になるため14分の短縮です。

詰め込みのときの荷室作業の割合（17〜19%）が、実測の18%とほぼ一致する点は、モデルの妥当性の裏付けとして見ています。前提を変えた感度分析でも、最も控えめな条件（降ろして戻す15秒・探す0秒）で1日27分の短縮が残り、5通りすべてで結論は変わりません。

## 向かないケース・残課題

- **1便で回れる運用**: 詰め込み満杯のほうが速いという結果です。配達順を守ると2便目が必要になり、拠点に戻る往復が荷室作業の削減を上回ります。分かれ目は36〜45分で、それ以下なら配達順どおりが有利になります。
- **再配達そのもの**: 空振りと再訪で1日約45〜70分の損失がありますが、これは積み方では減りません。積み方で減るのは、不在で持ち戻った箱が邪魔になる数分だけです（`docs/plan.md` §12）。
- **推定値への依存**: 「どかす・探す・助手席へ移す」の秒数は実測がなく、推定値です。だからこそ、前提を変えても結論が変わらないことを感度分析で示す形にしています。
- **実データでの検証**: 荷物はサンプル生成かCSVで、実運用のデータでは試していません。荷台寸法と軸重もデモ用の代表値です。

## まとめ

- 満杯にすることを目的にすると、配達順が崩れて荷室作業が増える
- 配達順を守れる量に抑え、減らした分を2便目に回すと、1個あたりの時間が下がる
- ただし1便で足りる規模では逆転するので、便数と往復時間で判断する
- 計画はラベルと手順書まで出して、初めて現場で再現できる

「もっと積む」ではなく「積みすぎない」を選ぶ、というのがこのツールの主張です。再配達の削減のように、積み方では解けない課題は別の仕組みに分ける。その切り分けも含めて、導入提案の材料になる形にしています。
