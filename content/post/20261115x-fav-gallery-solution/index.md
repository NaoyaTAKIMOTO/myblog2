## いいねは押した瞬間から埋もれていく

X を使っていて、あとから「あの画像をもう一度見たい」と思うことはよくあります。ところが実際に探そうとすると、次のような状態になっています。

- いいねは数千件を超え、いいねタブを遡るだけで一苦労する
- タイムラインは時系列で流れるので、同じ作家の別の絵と並べて見られない
- 画像の内容（構図・色・タッチ）では検索できない
- スクリーンショットを撮っても、フォルダの中で同じように埋もれる

つまり問題は「保存されていない」ことではなく、**保存されたものに到達する経路がない**ことです。Refav Gallery（リポジトリ名 `x-fav-gallery`）は、ここを「取り込み」「保存」「再発見」の3つに分けて作り直しました。この記事では、読者が同じ問題を自分の環境で解くときに再利用できる形で、設計とトレードオフを整理します。

## 既存手段の限界

まず、よくある手段と、それぞれがどこで止まるかを並べます。

| 手段 | できること | 限界 |
|---|---|---|
| X のいいねタブ | 押したものを時系列で見られる | 遡るほど目的の1件に届かない。内容からは探せない |
| X の検索 | 本文やアカウントで探せる | 画像の見た目では探せない。過去のいいねを対象にした検索もしにくい |
| スクリーンショットとフォルダ | 手元に残せる | 保存の手間が発生し、フォルダ内で同じように埋もれる |
| ブックマークアプリ | タグやフォルダで整理できる | 整理そのものが作業になる。取り込みは手動のまま |
| 自前で X API を定期 sync | 自動で集められる | 従量課金。個人の用途では費用が読みにくい |

共通しているのは、**「集める」か「整理する」のどちらかに寄っていて、集めたものを後から引き出す部分が弱い**ことです。Refav Gallery が狙ったのは、収集を自動化したうえで、引き出す側に類似画像という手がかりを持たせることでした。

設計の要点は4つです。

- **取り込みは「見ている間」に済ませる**: Chrome 拡張が X の通信を横から読み、X API を叩かない
- **履歴はアーカイブで補う**: 過去分は X 公式アーカイブの ZIP を取り込む
- **引き出しは類似画像**: DINOv2 の埋め込みを pgvector に置き、近い画像を候補にする
- **並べ方は多様性を混ぜる**: 同じ絵柄で埋まらないよう MMR で並べ替える

ここで意識したトレードオフが2つあります。

1つ目は、**完全な自動同期を捨てた**ことです。API の定期 sync は確実ですが従量課金で、個人が費用を読みながら使い続けるには向きません。代わりに、ユーザーが実際に開いた範囲だけを拾う passive な取り込みにしました。取りこぼしはアーカイブ取り込みで補えるので、日常の導線は拡張、履歴は ZIP、という分担にしています。

2つ目は、**検索を作り直すのをやめた**ことです。リポジトリでは 2026-08-06 に検索機能を一旦全廃止しました（本番適用は migration 066）。使われ方が伸びず、ベクトル用のテーブルが DB のバッファを占有して、ギャラリー本体の表示を押し下げていたためです。残したのは作者フィルタで、これはベクトルもモデルも使わない SQL だけで成立します。再発見の主役を「検索」から「類似画像と日次セレクション」に移した、という判断です。

## 実装の要点

### 取り込み: バッチで送って、重複はサーバーで落とす

拡張は、傍受した GraphQL 応答からツイートとメディア URL を組み立て、まとめて `POST /api/tweets` に送ります。

```ts
// chrome-extension/src/lib/api.ts
const response = await fetch(`${apiUrl}/api/tweets`, {
  method: 'POST',
  headers,
  // source: 取得元 = このクライアント (Chrome 拡張)。サーバは未指定を 'graphql' 既定にする。
  body: JSON.stringify({ tweets, collection, source: 'extension' }),
})
```

`collection` は `'like' | 'bookmark'` で、いいねとブックマークを別々に保持したうえで、ギャラリーでは重複を除いて統合表示します。同じツイート内の同じメディアは、取り込み経路によって URL の形が違っても `media_identity` の一意 index で1行に寄せています（別のツイートに再投稿された同一メディアは、再発見の挙動を変えないため統合しません）。

送信は50件ごとのバッチです（`INGEST_BATCH_SIZE`。サーバ側の上限100件の半分）。1件ずつ送ると、スクロールのたびに何十回も往復することになり、拡張の体感が悪くなります。かといって終了まで溜めると、タブを閉じたときに取りこぼします。50件ごとに送り、終了時に残りを流す形に落ち着きました。

### 履歴: アーカイブは「まず検出だけ」で試す

過去のいいねを一気に取り込むときは、X 公式アーカイブの ZIP を使います。いきなり本番に流し込む前に、検出だけを走らせるドライランがあります。

```bash
pnpm import:archive:dry
```

このコマンドは `scripts/import-archive.ts` に `--detect-all --dry-run` を渡すもので、ZIP の中にどんな種類のメディアがどれだけ入っているかを先に確認できます。アーカイブは形式が変わることがあるため、**まず数だけ数える**という手順を踏んでおくと、取り込み後に「思ったより入っていない」という事故を減らせます。

### 再発見: 類似候補を取り、MMR で並べ替える

Lightbox を開くと、`GET /api/recommend?imageId=...` が類似候補を返します。サーバー側は、ユーザーのコレクションが2万件以下なら自分のコレクション内で exact KNN を回し、それを超えるとグローバル HNSW に切り替えます。返す前に MMR（λ=0.7）をかけるので、同じ作家の連投で候補が埋まることはありません。

この「似ているが同じではない」並びが、埋もれたいいねを掘り直すときの手がかりになります。目的の画像を1枚見つければ、そこから同じタッチの別の画像へ渡り歩けるからです。

## 結果

リポジトリに残っている計測値です。

| 項目 | 変化 | 出典 |
|---|---|---|
| 類似画像検索（HNSW 導入前後） | 142 ms → 1.3 ms | `docs/operations/query-tuning-notes.md` |
| レコメンド関数（ローカル計測） | 78 ms | 同上 |
| 追加読み込みの既読率 | 57.9% → 42.1% | `docs/課題.md`（2026-09-18 実測） |
| 並びの平均 age | +16.7% | 同上 |
| ギャラリー初回表示の SQL | 約1.1 秒 → 0.45〜0.64 秒 | `docs/PROJECT_STATUS.md` |

既読率の改善は、「古い × まだ見ていない」に重みを置くランキングを入れた結果です。3関数 × 3規模の性能検証では +9% 以内に収まったと記録されています。つまり、並びを変えても表示は遅くなっていません。

体感として残ったのは、**探す行為が「遡る」から「眺める」に変わった**ことです。目的の画像が決まっているときは作者フィルタで絞り、決まっていないときは類似画像と日次セレクションを眺める。この2つのモードに分かれたことで、数千件のいいねが「読まない在庫」ではなくなりました。

## 向かないケース・残課題

- **いいねが数十件の人**: 類似候補の母数が足りず、レコメンドのありがたみが出ません。アーカイブ取り込みで母数を増やすか、時系列表示のままで足ります。
- **本文の全文検索をしたい人**: 検索は 2026-08-06 に一旦全廃止しました。作者フィルタ以外の語句検索は現時点で提供していません。
- **拡張に X の通信を読ませたくない人**: 取り込みはブラウザ拡張かモバイルアプリが前提です。公式アーカイブ ZIP だけでも履歴は入りますが、日常の自動取り込みは使えません。
- **複数人で共有したい場合**: 個人用として作っているため、他人のコレクションをまとめて見る用途は想定していません。
- **iOS の配布コスト**: アプリは `expo-updates` を使っておらず OTA 更新がありません。JS だけの変更でもストア配布が必要で、公開済みバージョンには新しい build を差せないため、変更のたびに `mobile/app.json` の version と buildNumber を上げています。
- **取り込みの取りこぼし**: passive な取得は、ユーザーが実際にスクロールした範囲に依存します。API による能動的な再取得は admin で検証中の段階で、全ユーザーには提供していません。

## まとめ

- 「保存されていない」のではなく「到達経路がない」と捉えると、作るべきものが変わる
- 取り込みは課金を避ける経路（passive + アーカイブ）に寄せ、完全自動は諦める
- 引き出しは検索ではなく類似画像と多様性のある並びで作る
- 使われない機能は、資源を本流に返してから別の形で作り直す

同じ構造は、写真の整理にも、読んだ記事の再読にも、買った本の再発見にも使えます。大事なのは、集める仕組みより**引き出す仕組みを先に設計する**ことでした。
